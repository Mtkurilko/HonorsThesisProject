Post-Quantum Cryptography in Practice

Benchmarking, Protocol Integration, and Migration Strategy for Real Systems
Michael Kurilko
Thesis Mentor: Dr. Joseph Kirtland  |  Marist University Honors Program

Introduction

Public-key cryptography is one of the quiet assumptions behind almost every modern system. Online banking, messaging, software updates, and logins all rely on RSA and elliptic-curve cryptography (ECC).

RSA is secure because factoring very large numbers is slow, and ECC relies on a related hard problem. A large enough quantum computer running Shor’s algorithm could solve both [1]. RSA and ECC are not broken today, but their security margin is not future-proof.

Health, legal, financial, and government records need to stay private for decades, so they are at risk before the hardware even exists.

If this is true, the data is already at risk [2]. Breaking RSA-2048 is still estimated to need millions of qubits [3], but waiting for an exact date is a poor plan.

Research Question

How can NIST-selected post-quantum algorithms be integrated into real application workflows while keeping performance and deployment risk manageable?

Motivation

I chose this topic after exploring current technology problems that felt both important and genuinely interesting to me. I wanted something that blended math and computer science, and post-quantum cryptography stood out because it has both deep theory and real-world urgency.

The biggest thing I learned is that adoption is not as simple as picking a new algorithm and replacing the old one.

Background

In 2024, NIST published two post-quantum standards: ML-KEM (FIPS 203) for establishing shared keys [4] and ML-DSA (FIPS 204) for digital signatures [5]. Both are based on lattices.

Lattice Problems

Imagine being dropped into a city with millions of nearly identical streets and asked to find one tiny shortcut using noisy map coordinates. In 2D this is manageable. In hundreds of dimensions (ML-KEM-512 uses 512), it becomes computationally hard.

Learning With Errors

Without noise
3x + 2y = 12
x + 4y = 14
Solution: x = 2, y = 3
With small errors
3x + 2y ≈ 13
x + 4y ≈ 13
No exact solution

Each equation has a small random error added. Without the errors the system is easy to solve, but with them, recovering the hidden values becomes hard in high dimensions [6].

ML-KEM Key Exchange

1. Key generation. The receiver creates a public key (like an open padlock) and a private key.
2. Encapsulation. The sender uses the public key to lock up a random shared secret and sends it.
3. Decapsulation. The receiver uses the private key to recover the same secret.

Hybrid Key Exchange

ECDH secret
+
ML-KEM secret
→
session key

The hybrid mode derives the session key from both a classical and a post-quantum secret, so security does not rely on only one assumption.

Key Terms

Handshake: the setup step where two devices agree on a secret before sending data.
Signature: proof that data came from the claimed sender and was not modified.
Latency: time for one operation (lower is better).
Throughput: work completed per second (higher is better).

Methods

I built a Python benchmarking framework that runs the same tests with RSA-2048, ECC (P-256), ML-KEM-512, ML-DSA-44, and a hybrid ECC + ML-KEM handshake. Each benchmark was repeated 1,000 times.

Workload layer
Messaging sessions, file transfer, and TLS-style handshakes
Benchmark layer
Latency, throughput, bytes sent, and memory, exported to CSV
Crypto layer
One shared interface, so algorithms can be swapped without rewriting the application

Keeping the layers separate made it possible to test each algorithm without changing the workload code, which is a practical example of crypto-agility.

If classical handshakes are like sending a short postcard, post-quantum handshakes are like sending a padded envelope. One envelope is fine, but millions per day change cost and latency, especially on mobile and edge networks [8].

Limitations

All tests ran on one machine without a real network and used a simplified message cipher, so the results compare algorithms rather than predict a live system. Future work includes network emulation, AES-GCM, ML-KEM-768, and hardware accelerators [9].

Results: Workloads

With session reuse, post-quantum handshakes took less than 1% of total messaging time, while RSA handshakes took 16%.

Migration Roadmap

0
Inventory and baseline
Map where RSA and ECC are used and record current metrics.
Gate: baseline data is complete and reproducible
1
Crypto-agility refactor
Make algorithms swappable at the interface level.
Gate: swaps need no application rewrites
2
Targeted hybrid deployment
Use hybrid first on long-lived, high-value channels.
Gate: error rates and latency stay in budget
3
Post-quantum preferred
Default to post-quantum where support is stable, with a fallback.
Gate: stable and interoperable in production
4
Governance and re-testing
Enforce crypto policy in CI/CD and re-benchmark over time.

Conclusion

Post-quantum algorithms are already fast enough for real systems. The main costs are larger messages and the engineering work of migrating safely, so the transition should be treated as a systems engineering program, not only a cryptographic substitution task.
